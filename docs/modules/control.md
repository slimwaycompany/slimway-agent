## Положение «Система оценки качества работы менеджеров» (документ Сергея, 06.11.2026)

### Принцип
- Не штрафовать за каждую ошибку: понятные стандарты, помощь в соблюдении, поощрение качества. Инструмент управления, не наказания.
- Менеджер должен понимать, что от него требуется и что сделать, чтобы получить полную переменную часть.

### Оплата смены
- Сейчас смена = 15 000 ₸. Делим: **10 000 ₸ фикс** (выход на смену и основные обязанности) + **5 000 ₸ переменная** = 5 стандартов × **1 000 ₸ за смену**.
- Максимум 15 000 ₸ за смену при соблюдении всех пяти.
- Связь с ЗП: `computePayroll` сейчас считает `shift_rate × смены` (`reports.md`) — нужно будет считать фикс × смены + сумма выполненных стандартов по сменам.

### 5 стандартов
1. **Скорость обработки заявок** — первый контакт с новой заявкой в течение **5 минут**.
2. **Качество взаимодействия с клиентом** — выяснила потребности, презентовала, ответила на вопросы, отработала возражения, довела до понятного результата. Видно по истории взаимодействия.
3. **Правильное заполнение карточки заявки и клиента** — сведения о клиенте, потребностях, источнике, текущем статусе; своевременно и достоверно, чтобы любой сотрудник мог продолжить.
4. **Работа с существующей базой** — напоминания об окончании абонементов, предложение продления, информирование, запланированные контакты, работа с теми, кто интересовался раньше. Не терять действующих клиентов.
5. **Посещаемость и списание занятий** — вовремя отмечать фактические посещения, контролировать остатки, без расхождений между расписанием, посещениями и балансом абонемента.

### Как проверяем (по положению)
- **Проверяющий сотрудник ежедневно** смотрит работу по всем 5 стандартам: карточки заявок и клиентов, историю взаимодействий, старую базу, расписание, посещения.
- По каждому недочёту менеджер получает: где (карточка/процесс), что исправить, как правильно, что в первую очередь.
- **Можно исправить** — если недочёт устраним, менеджеру дают исправить в установленном порядке.
- **Причина важна** — техсбой, нет данных, обстоятельства не по вине менеджера → не нарушение.

### Принцип «код vs настройки»
- **В коде** — только *типы автопроверок* (как система находит факт: звонок АТС, запись, задача, замер, статус визита). Новый тип автопроверки = задача Claude Code.
- **В настройках (CRM, без кода)** — всё остальное: роли и их линейки, состав пунктов, названия и описания, из каких проверок собран пункт, параметры (минуты, дни, окна), ручные пункты, кто проверяет, сроки проверки, деньги и прощения, вкл/выкл, видимость для девочек.
- **Ручной пункт** создаётся из CRM без кода: «проверяющий ставит есть/нет» по списку объектов (смена / сеанс / пробное / продажа / фото отметки). Так делаются «Форма», «Анкета», «Рег. форма», «Расписание (ОКК)» и любые будущие («Чистота зала» и т.п.).
- **Версии**: изменение линейки действует с даты (`effective_from`); прошлые дни считаются по правилам, действовавшим тогда. Пересчёт задним числом — только кнопкой admin.

### Сущности
- **Роль смены**: call center, консультант (+ будущие). Роль задаётся на каждую смену (график / отметка), девочка может быть в разных ролях в разные дни.
- **Линейка роли**: фикс за смену, цена пункта, макс. переменная часть, сколько нарушений прощается (CC — 1, консультант — 0), формула (CC: 0–1 → 5 000, 2 → 3 000, 3 → 2 000, 4 → 1 000, 5–6 → 0; консультант: (5 − v) × 1 000), когда итог окончательный (CC — утро след. дня; консультант — после проверки ОКК, авто-зачёт через 7 дней).
- **Пункт**: название, описание для девочек, порядок, вкл/выкл, состав = набор проверок (авто и/или ручных); пункт нарушен, если нарушена хоть одна его проверка.
- **Проверка**: тип (из каталога кода) + параметры + источник данных + «кто проверяет» (система / роль ОКК / admin).
- **Нарушение**: смена, пункт, проверка, кому, что не так, как исправить, **доказательство** (ссылка на звонок/запись АТС, карточку, визит, фото), статус (открыто / исправлено / не исправлено / снято / оспорено), кто и когда решил.

### Каталог автопроверок (в коде, с параметрами)
- CC: скорость с очередью (АТС: свободна → +время фиксации → N мин; пропущенный = лид); B.A.N.T. (N и T есть к концу звонка + время фиксации; звонок > 60 сек; первый разговор); запись только сегодня/завтра + «Решение после» с задачей на завтра; исход после разговора; задачи в срок с контактом (перенос без контакта = нет); follow-up — материалы через скриптолог за N мин, кружок накануне (отметка), живое сообщение (исходящее не по шаблону), автонапоминания.
- Консультант: InBody/замер тела по графику (пробное — InBody; 1-е посещение и последнее — оба; InBody раз в 7 дней; тело раз в 30 дней при абонементе > месяца); статусы визитов не висят; «пришла» с правильного абонемента; отмены статусом; нет двойных записей.
- Обе: опоздание (приход за 15 мин до «Факта» графика, уход; доверенный ПК + фото).

### Экраны
- **Настройки → Контроль**: Линейки ролей · Пункты (конструктор: добавить / переименовать / собрать из проверок / ручной пункт) · Параметры проверок · Деньги и прощения · Доступы (право «Контроль», роль ОКК, видимость вкладок) · Доверенные ПК · Время фиксации после звонка · Тексты/сроки автонапоминаний.
- **Отчёты → Менеджер → Контроль**: две вкладки **«Контроль call center»** и **«Контроль консультант»**; сотрудники × пункты по дням; календарь; клик → нарушения с доказательствами; «не по вине», пересчёт.
- **Очередь ОКК**: всё, что ждёт глаз (сеансы для сверки, фото формы, анкеты/рег. формы) — быстрые кнопки «верно / ошибка + комментарий»; счётчик «ждёт проверки», дедлайн 7 дней.
- **«Моя смена» у девочки** (после теста): живой статус её пунктов сейчас + «что исправить прямо сейчас» + деньги за смену; оспорить нарушение (admin решает).
- **Овчарка** (после теста): только то, что можно исправить сейчас (лид ждёт в очереди, задача сгорает, материалы не отправлены).
