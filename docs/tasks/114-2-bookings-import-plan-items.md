ЧАСТЬ 0 — Подготовка

- `git pull --rebase origin main`, `git status`. Прочитать `CLAUDE.md`, `docs/modules/crm-schedule.md`, `src/jobs/fitbaseBookingsImport.ts`, `src/jobs/fitbaseHistoryImport.ts`, обработчик `POST /kviz/api/crm/client-plans/:id/split` в `src/http/crm.ts`.
- Причина: после 114.1 по первым 10 клиентам создано 2, в историю 85. Импорт истории (`fitbaseHistoryImport.ts`) создаёт `crm_client_plans` из договоров Fitbase, но не создаёт `crm_client_plan_items`. Поэтому почти каждая запись по абонементу уходит в историю с причиной `no_item`, а при пустом `plan_id` (название договора не совпало с каталогом) — с причиной `no_plan`.
- Ограничения `crm_bookings` те же, что в ТЗ 114.1 (check1: бронь `plan` требует `client_plan_id`, `client_plan_item_id`, `phase`; `plan_id` NOT NULL).
- Сплит (`/split`) вставляет позиции и ставит `needs_split=false`, существующие позиции не удаляет. Поэтому позиции для абонементов с `needs_split=true` автоматически НЕ создавать — их распределяют девочки вручную.

ЧАСТЬ 1 — Позиции для импортированных абонементов

- Новая функция `ensureImportedPlanItems(clientId)` в `fitbaseBookingsImport.ts`, вызывать для клиента перед загрузкой его абонементов (до `contractToEntry`).
- Берёт абонементы клиента: `source='fitbase'`, `plan_id` не null, `needs_split` не true, и у которых нет ни одной строки в `crm_client_plan_items`.
- Для каждого создаёт позиции по шаблону `crm_plan_items` его `plan_id` (одна позиция на строку шаблона): `device_type_code` / `device_type_codes` (пул), `phase`, `is_unlimited`, `daily_limit` — из шаблона.
- Сеансы:
  - в шаблоне одна позиция → `sessions_total` = `crm_client_plans.sessions_total` (если null — `sessions` шаблона), `sessions_left` = `crm_client_plans.sessions_left` (если null — 0);
  - в шаблоне несколько позиций (абонемент уже не активен, иначе стоял бы `needs_split`) → `sessions_total` = `sessions` шаблона, `sessions_left` = 0.
- Шаблон без позиций → ничего не создавать (записи этого абонемента уйдут в историю с `no_item`, как сейчас).
- Сеансы при переносе не списывать: перенос только вставляет брони, `sessions_left` позиций и абонемента не трогает.
- Новая причина «в историю» `needs_split`: договор найден, но у абонемента `needs_split=true` и позиций нет. Добавить в `to_history_reasons` и в подсказку на карточке.
- Счётчик `items_created` в статусе и строка «Создано позиций абонементов: N» в карточке.

ЧАСТЬ 2 — Чистка истории при успешной брони

- После успешной вставки брони (реальный аппарат, виртуальный или обновление по 23505) удалять строку `crm_visit_history` с тем же `fitbase_reg_id` — это хвосты прошлых прогонов, иначе визит задвоится (бронь + история).
- Удалять только строки с `fitbase_reg_id` не null; ручные записи истории не трогать.

ЧАСТЬ 3 — Расшифровка «пропущено»

- В статусе разделить и показывать в подсказке к «пропущено»: «нет аппарата: N», «неизвестный статус / нет времени: N».
- Собирать топ-10 названий мест Fitbase (`event.place.name`), по которым аппарат не найден, с количеством, и топ-5 неизвестных кодов статуса. Показать в той же подсказке.
- Виртуальные аппараты все заняты (сейчас тоже `skipped_no_device`) — отдельный счётчик «нет свободного виртуального: N».
