ЧАСТЬ 1 — Настройки → Воронки CRM: редизайн

Сейчас: одна длинная лента всех воронок, у каждого этапа текст `inbox/normal/success/fail` и кнопки «Редактировать» / «В архив»; порядок не меняется, удалить этап нельзя, системные этапы (общие, `funnel_id is null`) повторяются в каждой воронке.

Новый экран (`SettingsPage.tsx` → `FunnelsSection`, вынести в отдельный файл `kviz/client/src/pages/crm/settings/FunnelsSettings.tsx`):

Раскладка
- Десктоп/планшет: слева список воронок (узкая колонка), справа этапы выбранной воронки. Телефон (≤640): сначала список воронок, по тапу — этапы с кнопкой «← Назад».
- Выбранная воронка запоминается в localStorage (в try/catch).

Список воронок (левая колонка)
- Каждая строка: ручка перетаскивания ⋮⋮, название, число открытых заявок, бейдж «Неактивна» если `is_active=false`.
- Перетаскивание меняет порядок (`@dnd-kit` уже есть в проекте). Порядок = `crm_funnels.sort`, на доске «Воронка» вкладки воронок идут в этом же порядке.
- Двойной клик (на телефоне — пункт меню) по названию → поле ввода прямо в строке, Enter/потеря фокуса — сохранить, Esc — отменить. Пустое название не сохранять.
- Меню ⋯ воронки: «Переименовать», «Сделать неактивной / активной», «Загрузить из таблицы» (существующий reset-content, с тем же подтверждением), «Удалить».
- Кнопка «+ Воронка» внизу списка.
- Удаление воронки: если открытых и архивных заявок 0 — подтверждение и удаление вместе с её обычными этапами. Если заявки есть — окно «В воронке N заявок. Перенести их в воронку [выпадающий список] и удалить?»; заявки уходят на входящий этап целевой воронки (если он скрыт там — на первый обычный этап). Последнюю воронку удалить нельзя.

Этапы воронки (правая часть)
- Сверху закреплён «Неразобранные» (inbox), снизу закреплены «Успех» (success) и «Отказ» (fail). Между ними — обычные этапы этой воронки, их можно перетаскивать (ручка ⋮⋮). Системные не перетаскиваются.
- Строка этапа: ручка, цветная точка (клик — выбор цвета из палитры токенов, пишется в `color`), название, число заявок на этапе в этой воронке, бейджи по-русски вместо `inbox/normal/...`: «Входящий», «Успех», «Отказ», «Личный» (`is_personal`), «Скрыт» (`is_archived`). У обычного этапа бейджа типа нет.
- Двойной клик по названию → переименование в строке (как у воронки). Для системного этапа перед сохранением подсказка под полем: «Название поменяется во всех воронках» (этапы общие).
- Меню ⋯ обычного этапа: «Настроить» (открывает существующий `StageEditor` — памятка, подсказки, пункты, «Вернуть к таблице» — в боковой панели справа / bottom sheet на телефоне, а не внутри списка), «Переименовать», «Скрыть / Показать» (это прежний `is_archived`, кнопку «В архив» убрать), «Удалить».
- Меню ⋯ системного этапа: «Настроить», «Переименовать», «Скрыть в этой воронке / Показать». Пункта «Удалить» нет — вместо него серый текст «Системный этап удалить нельзя, можно скрыть». Причина: на них завязаны создание заявки (входящий), обязательная причина отказа и правило покупки.
- Скрытые этапы (обычные и системные) показываются внизу списка свёрнутым блоком «Скрытые (N)».
- Поле «Новый этап» + кнопка — одно, под обычными этапами; новый этап встаёт последним среди обычных (`sort = max + 10`).

Удаление обычного этапа
- Заявок на этапе 0 → подтверждение `showConfirm` → удаление.
- Заявки есть → окно «На этапе N заявок. Перенести в этап [выпадающий список этапов этой воронки, без удаляемого и скрытых] и удалить». Сервер переносит и удаляет одной операцией.

Скрытие системного этапа в воронке
- Хранится в `crm_funnels.hidden_system_kinds` (например `{'inbox'}`).
- Скрыть можно, только если в этой воронке на этом системном этапе 0 открытых заявок; иначе — то же окно переноса, что при удалении, затем скрыть.
- На доске «Воронка» скрытые системные этапы этой воронки не показываются. Ручное создание заявки (`POST /crm/leads`): если входящий этап у воронки скрыт — заявка встаёт на первый видимый обычный этап.

API (`src/http/crmLeads.ts`, только admin, всё в `crm_audit_log`)
- `PATCH /kviz/api/crm/funnels/reorder` `{ ids: string[] }` → `sort = индекс*10`.
- `PATCH /kviz/api/crm/funnel-stages/reorder` `{ funnel_id, ids: string[] }` → только обычные этапы этой воронки, `sort = индекс*10`. Чужие/системные id → 400.
- `PATCH /kviz/api/crm/funnels/:id` — добавить `hidden_system_kinds` (массив, только значения `inbox`/`success`/`fail`, иначе 400; при наличии заявок на скрываемом этапе в этой воронке → 409 `{error, count}`).
- `PATCH /kviz/api/crm/funnel-stages/:id` — уже принимает `name`, `color`, `is_archived`; добавить проверку: пустое имя → 400.
- `DELETE /kviz/api/crm/funnel-stages/:id?move_to=<stage_id>`:
  - `kind <> 'normal'` → 400 «Системный этап нельзя удалить — его можно скрыть в воронке».
  - есть заявки (включая архивные) и нет `move_to` → 409 `{ error, count }`.
  - с `move_to`: целевой этап в той же воронке или системный; заявки → `stage_id = move_to`, `stage_changed_at = now()`, запись в `crm_lead_activity` `kind='stage_change'`, текст «Этап «<старый>» удалён, заявка перенесена в «<новый>»», `author` = `display_name` из сессии; затем удалить этап.
- `DELETE /kviz/api/crm/funnels/:id?move_to_funnel=<funnel_id>` — по правилам выше. Без заявок — удалить обычные этапы воронки и саму воронку.
- `POST /kviz/api/crm/leads/bulk-move` `{ from_stage_id, funnel_id, to_stage_id }` — массовый перенос (для окна перед скрытием системного этапа); активность по каждой заявке.
- `GET /kviz/api/crm/funnels` — добавить в каждый этап `leads_count` (открытые, не архивные) для этой воронки и вернуть `hidden_system_kinds`. Подсчёт одним запросом группировкой, не запросом на этап.

Доска «Воронка» (`FunnelPage.tsx`)
- Порядок колонок: входящий (если не скрыт) → обычные по `sort` → Успех → Отказ (если не скрыты). Скрытые обычные этапы (`is_archived`) — как сейчас.
- Порядок вкладок воронок — по `crm_funnels.sort`.

Мобильная версия обязательна: список воронок и этапы — во всю ширину, меню ⋯ — bottom sheet, перетаскивание работает на тач (TouchSensor с задержкой 200 мс, чтобы не мешать прокрутке).

ЧАСТЬ 3 — Обновление экранов без перезагрузки (realtime)

Сейчас: доска опрашивает сервер раз в 60 с, остальные экраны обновляются только перезагрузкой. Supabase Realtime в браузере не используем (в браузере нет ключа Supabase, у таблиц RLS без политик — так и оставляем). Делаем свой канал событий на сервере (SSE), без SQL.

Сервер
- Новый файл `src/core/liveBus.ts`: `EventEmitter`, `emitLive({ topic, id?, action, by? })`. `topic` — одно из: `leads`, `funnels`, `lead_tasks`, `schedule`, `clients`, `kassa`, `plans`, `measure`, `manager`, `settings`.
- Middleware на `/kviz/api` (до роутеров): для `POST/PATCH/PUT/DELETE`, когда ответ завершился с кодом 2xx (`res.on('finish')`), определить topic по префиксу пути и вызвать `emitLive`. Таблица префиксов (дополнить по фактическим маршрутам):
  - `/kviz/api/crm/leads`, `/crm/lead-tags`, `/crm/lost-reasons` → `leads`
  - `/crm/funnels`, `/crm/funnel-stages` → `funnels`
  - `/crm/lead-tasks`, `/manager/tasks` → `lead_tasks`
  - `/crm/schedule`, `/crm/booking-labels` → `schedule`
  - `/crm/clients`, `/crm/client-tags`, `/crm/client-comments`, `/crm/client-plans`, `/crm/body-clients` → `clients`
  - `/crm/kassa`, `/crm/shifts`, checkout/refund → `kassa` (продажа/возврат дополнительно → `clients` и `schedule`)
  - `/crm/plans`, `/crm/plan-items`, `/crm/promo-codes`, `/crm/products`, `/crm/payment-methods` → `plans`
  - `/measure/*`, `/inbody/*` → `measure`
  - прочие `/crm/*` справочники → `settings`
  - `id` — из `req.params.id`, если есть; `by` — id сессии пользователя.
- Фоновые задачи, которые меняют данные (`runCrmLifecycle`, агент пробных, автоматика воронки `runLeadRules`, импорт) — явно `emitLive` после записи.
- `GET /kviz/api/live` — SSE: только с входом (без входа 401 JSON, как все `/api/*`), заголовки `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`, `res.flushHeaders()`, `retry: 3000`, пинг-комментарий каждые 25 с, отписка от шины на `close`. Сообщение: `data: {"topic","id","action","by"}`. Ограничение: не больше 5 потоков на одну сессию (старые закрывать).

Оболочка
- `public/shell-app.js`: один `EventSource('/kviz/api/live')` на всю оболочку (не в каждом iframe — лимит соединений браузера), события пересылать во все iframe вкладок через `postMessage({ type: 'live', topic, id, action, by })`. При обрыве — переподключение (EventSource сам), при возврате на вкладку браузера после >60 с скрытия — разослать `{type:'live', topic:'*'}` (всем перечитать).

React-приложение
- `kviz/client/src/lib/live.ts`: хук `useLive(topics: string[], onChange: (e) => void)` — слушает `message` от родителя, фильтрует по topic (или `*`), дебаунс 400 мс.
- Подключить:
  - Доска «Воронка» (`FunnelPage`): `leads`, `funnels`, `lead_tasks` → перечитать список (существующий `loadLeads`), но не трогать карточку, которую тащат, и открытые попапы (как сейчас для 60-секундного опроса). Опрос раз в 60 с убрать, оставить страховочный раз в 5 мин.
  - Карточка заявки (`LeadDrawer`): `leads` с её `id` → перечитать ленту и поля, если форма не редактируется (есть несохранённые правки — показать плашку «Заявка изменена другим сотрудником · Обновить»).
  - Настройки → Воронки: `funnels`.
  - Расписание: `schedule`.
  - Клиенты: список и открытая карточка — `clients`, `kassa` (по `id`, если совпадает с открытым клиентом; список — тихо перечитать текущую страницу).
  - Касса: `kassa`.
  - Менеджер (задачи): `lead_tasks`, `manager`.
  - Замеры: `measure`.
- Событие от самого себя (`by` = своя сессия) не перечитывать там, где экран уже обновился после своего запроса.
