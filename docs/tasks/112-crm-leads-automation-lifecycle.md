ЧАСТЬ 1 — Движок правил (сервер)

Файлы: `src/core/automation/conditions.ts` (каталог условий), `src/core/automation/engine.ts` (`runAutomation({ ruleId?, clientIds?, dry? })`), маршруты в `src/http/crmAutomation.ts` (смонтировать в `kviz.ts` рядом с `buildCrmLeadsRouter`).

Правило (`crm_automation_rules`): `name`, `target_funnel_id` + `target_stage_id` (куда переносить), `source_scope` jsonb `{ funnel_ids: [], stage_ids: [] }` (пусто = из всех воронок), `match` (`all`/`any`), `conditions` jsonb — массив `{ type, params }`, `actions` jsonb `{ create_lead_if_missing: bool, task: { type_id, text, due_in_hours, responsible: 'lead_manager'|'all_managers'|<user_id> } | null }`, `mode`, `priority` (меньше — важнее), `last_run_at`, `last_run_stats` jsonb.

Каталог условий (тип → параметры → смысл). Данные клиента — только из нашей CRM: `crm_client_plans` (+ `crm_plans`, `crm_client_plan_items`), `crm_bookings`, `crm_visit_history`, `crm_sales`, `crm_lead_tasks`. Fitbase не вызывать.
- `has_active_plan` `{}` — у клиента есть действующий купленный абонемент: `crm_plans.kind='abonement'`, не бесплатный (`is_free_booking=false`, не системный), полная цена ≥ `automation.min_plan_price` (по умолчанию 40 000 ₸, цена до скидок), статус «активен» (или «не активирован», но оплачен — включить, так это тоже купленный). Замороженный считается действующим. Безлимитный — тоже.
- `plan_days_left_lte` `{ days }` — у действующего абонемента до конца срока (`valid_until`, с учётом `extra_until`, если есть) ≤ N дней. Если абонементов несколько — берётся самый поздний срок.
- `plan_sessions_left_lte` `{ sessions }` — суммарный остаток занятий по всем действующим абонементам ≤ N. Безлимитные пункты не считаются; если все пункты безлимитные — условие ложно.
- `plan_ended_days` `{ from, to }` — действующего абонемента нет, последний купленный закончился от `from` до `to` дней назад (`to` пусто = без верхней границы).
- `trial_attended_no_purchase` `{}` — у клиента есть запись на пробное (бесплатная бронь системной услуги «Пробное занятие») со статусом `attended`, и после неё нет покупки абонемента.
- `days_on_stage_gte` `{ days }` — заявка на текущем этапе ≥ N дней (`stage_changed_at`).
- `no_future_task` `{}` — у заявки нет открытой задачи со сроком в будущем (`status='open'` и `due_at > now()`).
- `days_since_last_visit` `{ from, to }` — последний визит (`crm_bookings.attended` + `crm_visit_history.attended`) от `from` до `to` дней назад.
- `days_since_created` `{ from, to }` — заявка создана от `from` до `to` дней назад (для «грейда» по давности).

Работа движка
- Берёт неархивные заявки (для условий по клиенту — только с `client_id`) и включённые правила (`mode <> 'off'`), сортировка правил по `priority`.
- Данные грузить пачками на всех клиентов сразу (несколько запросов `in(...)`), не запрос на заявку.
- Для каждой заявки — первое по приоритету правило, у которого: заявка в `source_scope`; заявка ещё не на целевом этапе; условия выполнены (`all` — все, `any` — хотя бы одно). Остальные правила для этой заявки в этом прогоне не смотреть (одна заявка — максимум один перенос за прогон).
- Ручной перенос важнее автоматики: если сотрудник переносил заявку вручную (`crm_lead_activity` `kind='stage_change'` с автором-человеком) за последние `automation.manual_hold_hours` (по умолчанию 24) — пропустить, в журнал `skip` с причиной.
- У клиента несколько открытых заявок — двигать только последнюю (по `stage_changed_at`), остальные не трогать.
- `create_lead_if_missing` (только если в правиле есть условие по абонементу): у клиента нет открытой заявки → создать: `origin='manual'`, `tags=['auto']`, `title` = «<Фамилия Имя>», имя/телефон/`client_id` из клиента, `budget=0`, сразу на целевой этап; лента — `system` «Заявка создана автоматизацией: правило «…»».
- Режим `test`: ничего не менять, только писать в `crm_automation_log` (`mode='test'`), что было бы сделано.
- Режим `live`: `stage_id`, `funnel_id`, `stage_changed_at=now()`; в ленту `stage_change` «[АВТО] Правило «<имя>»: <воронка/этап> → <воронка/этап>», автор «Автоматизация»; задача из `actions.task` (с защитой от дубля, как в `leadRules.ts`); `crm_audit_log`; `emitLive('leads')` (шина из ТЗ 111).
- Итог правила → `last_run_at`, `last_run_stats` `{ matched, moved, created, skipped }`.
- Журнал хранить 30 дней (удалять старое в конце прогона).

Когда запускается
- `POST/GET /run/crm-automation` (защита `CRON_SECRET`, лок 10 мин, 202) — Сергей ставит в cron-job.org каждые 15 минут.
- Сразу после событий клиента (fire-and-forget, только по этому клиенту, `clientIds:[id]`): продажа и возврат (`crm_checkout`/`crm_refund` в Кассе), смена статуса брони в Расписании, заморозка/разморозка абонемента.

API (право `settings.automation`, всё в `crm_audit_log`)
- `GET /kviz/api/crm/automation/rules` — правила + имена воронок/этапов + `last_run_stats`.
- `POST`, `PATCH /:id`, `DELETE /:id` — проверки: целевой этап существует и принадлежит целевой воронке (или системный и не скрыт в ней); типы условий только из каталога; параметры — целые ≥ 0, `from ≤ to`.
- `PATCH /kviz/api/crm/automation/rules/reorder` `{ ids }` → `priority = индекс*10`.
- `POST /kviz/api/crm/automation/rules/:id/preview` — прогон только этого правила в режиме `test` без записи в журнал, ответ: до 100 заявок `{ lead_id, title, from, to }` + общее число.
- `POST /kviz/api/crm/automation/run` — запустить всё сейчас (кнопка «Запустить сейчас»).
- `GET /kviz/api/crm/automation/log?rule_id=&mode=&limit=200`.
- `GET/PUT /kviz/api/crm/automation/settings` — `automation.min_plan_price`, `automation.manual_hold_hours`.

Права: добавить `settings.automation` в `PERM_CATALOG` (`src/core/permissions.ts`), admin — по умолчанию.

- Общие параметры (свёрнуто): «Абонемент считается купленным от ___ ₸», «Не трогать заявку ___ ч после ручного переноса».

Список правил
- Группировка по целевой воронке (заголовок группы — название воронки), внутри — карточки в порядке приоритета, перетаскивание меняет приоритет (в пределах всего списка).
- Карточка правила — читаемая фраза, без кодов:
  - строка 1: название правила и бейдж-переключатель «Выкл / Тест / Боевой» (сегменты, цвета по токенам: серый / жёлтый / зелёный);
  - строка 2: «→ <Воронка> / <Этап>» с цветной точкой этапа;
  - строка 3: условия человеческим языком, например «Есть абонемент и (до конца ≤ 10 дней или осталось ≤ 3 занятий)», «Откуда: из всех воронок»;
  - строка 4 (серым): «Последний прогон: подошло 12, перенесено 10, пропущено 2» (в режиме Тест — «перенесло бы 12»);
  - меню ⋯: «Изменить», «Проверить сейчас», «Журнал», «Дублировать», «Удалить» (подтверждение).
- Кнопка «+ Правило».
- Перевод правила в «Боевой» — подтверждение «Правило начнёт переносить заявки. Последняя проверка: N заявок» (N — из `preview`).

Редактор правила (боковая панель справа; телефон — bottom sheet)
- «Название».
- «Куда переносить»: воронка → этап (выпадающие списки, этапы выбранной воронки, включая системные видимые).
- «Откуда забирать»: «Из всех воронок» или выбор воронок/этапов (мультивыбор).
- «Условия»: переключатель «Все условия / Любое из условий», список условий, «+ Условие» → выпадающий список каталога с понятными названиями: «Есть купленный абонемент», «До конца абонемента ≤ … дней», «Осталось занятий ≤ …», «Абонемент закончился от … до … дней назад», «Пришла на пробное и не купила», «На этапе ≥ … дней», «Нет задачи с датой в будущем», «Последний визит от … до … дней назад», «Заявка создана от … до … дней назад». Поля чисел — с подписью единиц.
- «Действия»: галочка «Создать заявку, если у клиента её нет» (видна только при условии по абонементу); «Поставить задачу» — тип (из `crm_task_types`), текст, через сколько часов, кому (менеджеру заявки / всем менеджерам / сотрудник).
- Кнопка «Проверить» — показывает результат `preview` списком под формой (заявка, откуда → куда), до 100 строк + «и ещё N».
- «Сохранить» / «Отмена».

Журнал
- Модальное окно: дата, режим, заявка (клик → `LeadDrawer`), действие, откуда → куда, причина пропуска. Фильтры: правило, режим.

Блок «Задачи по заявкам» (ниже правил)
- Два прежних правила `crm_lead_rules` (`lead_first_contact`, `stage_task`) — карточками с переключателем Вкл/Выкл и понятной формой параметров (тип задачи, текст, срок, воронка/этап) вместо сырого JSON. Логику `leadRules.ts` не менять.

Мобильная версия обязательна (`npm run check:mobile` для нового экрана).
