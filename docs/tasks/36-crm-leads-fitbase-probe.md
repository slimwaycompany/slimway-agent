ЗАДАЧА: CRM Воронка — шаг 1. Проверка API Fitbase для переноса воронок (только чтение, отчёт)
═══════════════════════════════════════

Перед началом прочитай CLAUDE.md, docs/STATE.md, docs/modules/crm-leads.md, docs/modules/agent.md, docs/modules/reports.md, docs/QUEUE.md.

Цель: понять, что отдаёт Fitbase API v2 по заявкам, воронкам, этапам, тегам, задачам, комментариям и статусам клиентов. По отчёту будет написан SQL таблиц нашей воронки. В этой задаче ничего не создаём в базе и ничего не меняем в Fitbase.

═══════════════════════════════════════
ЧАСТЬ 1 — Зонд probeLeadsApi
═══════════════════════════════════════

Новый файл src/jobs/probeLeadsApi.ts, эндпоинт GET /run/probe-leads-api (защита CRON_SECRET, как у других probe-*), синхронный, отдаёт JSON.
Все обращения к Fitbase — только через src/http/fitbase.ts (rawGet). Никаких rawPost, PATCH, PUT, DELETE.
page_size не больше 100, пагинация до пустой или неполной страницы, пауза 300–500 мс между страницами, 4xx не ретраить, circuit breaker не обходить.
Агента жизненного цикла и другие задачи не запускать и не трогать.
В JSON и в отчёте маскировать персональные данные: телефон +7 7•• ••• ••12, ФИО — первая буква + •••, ИИН не выводить.

═══════════════════════════════════════
ЧАСТЬ 2 — Что выяснить
═══════════════════════════════════════

Для каждого пункта: эндпоинт, параметры фильтрации, пример ответа (1–2 записи, замаскированные), полный список полей с типами, количество записей.

Воронки и этапы — /purchase-funnel-step (и есть ли отдельный эндпоинт списка воронок):
все воронки: id, название;
все этапы: id, название, воронка, порядок, цвет, системный ли этап (Неразобранные, Успех, Отказ);
ожидаемые воронки: «Новые заявки», «Новички», «Постоянные клиенты», «Реактивация». Включая личные этапы «Ангелина», «Вера», «Назерке».
Заявки — /lead и /lead/:id:
все поля списка и деталки, чем они отличаются;
есть ли поля: название, описание, бюджет, теги, менеджер, воронка, этап, источник, UTM (компания, источник, канал, фраза, контент), клиент, телефон, даты создания и изменения, архив, удалено;
как получить архивные заявки и заявки в «Отказ» (параметр фильтра?);
есть ли фильтр по дате изменения (updated_at / updated_from) — для быстрой синхронизации раз в 5 минут только изменённых;
сколько всего заявок: по воронкам, по этапам, отдельно архивных.
Теги — есть ли эндпоинт справочника тегов; в каком виде теги приходят в заявке (id / строка). Проверить, что есть tiktok, manual_import, no_phone.
Задачи — /task:
фильтр по заявке и по клиенту;
поля: тип/категория, текст, срок, исполнитель, автор, статус, дата выполнения;
есть ли справочник категорий (сейчас известны 2 «Звонок», 5 «Задание»);
как по ответу понять «срок подошёл / просрочена» (розовая карточка в Fitbase).
Комментарии — /note:
фильтр по заявке; поля: текст, автор, дата, тип;
приходят ли туда сообщения мессенджеров (WhatsApp, fitbase_chat) или только комментарии.
Клиенты — /client/:id:
поле статуса клиента (Закрыт / Открыт / Новый / Потенциальный): название поля, значения, коды;
если есть цвет статуса — какой у какого.
Справочники:
менеджеры и пользователи (эндпоинт, поля id и ФИО);
рекламные источники (эндпоинт, id, название).
Производительность: сколько запросов и времени занимает полный обход всех заявок и задач. Укладывается ли синхронизация раз в 5 минут на бесплатном Render.

ЧАСТЬ 3 — Отчёт
═══════════════════════════════════════

Файл docs/reports/fitbase-leads-api.md по пунктам 1–8 из ЧАСТИ 2: эндпоинт, параметры, поля с типами, замаскированный пример, количество.
Отдельный раздел «Чего нет в API» — что видно в интерфейсе Fitbase, но не отдаётся API.
Отдельный раздел «Предложение для синхронизации»: полная или инкрементальная, ключи для связи (id заявки, id клиента, id этапа, id менеджера).
Полную таблицу воронок и этапов (id, название, порядок, цвет) вывести в отчёт целиком — по ней будет SQL.
SQL не писать и SQL-файлы не создавать. Схему таблиц напишет Claude в чате по этому отчёту.
