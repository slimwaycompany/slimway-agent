# SlimWay Agent — правила проекта

Этот файл читают все ИИ-агенты, которые работают с проектом (Claude Code — `CLAUDE.md`, Codex — `AGENTS.md`). Содержание обоих файлов одинаковое. Меняешь одно — поменяй и второе.

## 0. С ЧЕГО НАЧАТЬ (обязательно, каждый раз)

Перед любой задачей прочитай по порядку:
1. Этот файл целиком.
2. `docs/STATE.md` — карта модулей, их статус и последние изменения.
3. `docs/modules/<модуль>.md` — файл того модуля, к которому относится задача (в ТЗ первой строкой указано `Модуль: <имя>`). Если задача задевает несколько модулей — прочитай все их файлы.
4. `docs/QUEUE.md` — очередь задач.

Не начинай писать код, пока не прочитал файл модуля: там решения, которые уже приняты, и баги, которые уже известны. Если ТЗ противоречит файлу модуля — остановись и спроси.

**После задачи — обязательно обнови документацию** (раздел 8). Задача без обновлённого файла модуля не считается выполненной.

## 1. Что это за проект

Помощник студии SlimWay (Астана): сервер `slimway-agent`, рабочее окно для сотрудников и своя CRM, на которую студия позже переедет с Fitbase.

- **Сервер:** Node.js + Express + TypeScript, точка входа `src/index.ts` (папки `src/core`, `src/db`, `src/http`, `src/jobs`).
- **Хостинг:** Render, бесплатный инстанс (512 МБ, один процесс), автодеплой из ветки `main` репозитория `slimwaycompany/slimway-agent`. Адрес: https://slimway-agent.onrender.com
- **База:** Supabase (Postgres). Сервер ходит через `service_role`, у всех таблиц включён RLS без политик.
- **Расписание:** cron-job.org дёргает эндпоинты `/run/*` (защищены `CRON_SECRET`).
- **CRM сейчас:** Fitbase (API v2). Все обращения к Fitbase держать в одном модуле.
- **Своя CRM:** таблицы `crm_*` в той же базе. Пока каркас — с Fitbase не синхронизируется и ничего в Fitbase не пишет.
- **Скриптолог:** Chrome-расширение `extension/` + страница `/scriptolog` — скрипты продаж в боковой панели рядом с чатом Fitbase.

### Рабочее окно (то, что видят сотрудники)

- `/login` — вход по личному логину (таблица `app_users`, роли `admin` / `manager`). Пароль проверяет функция БД `app_check_login`. Cookie сессии: `Path=/`, HttpOnly, Secure, SameSite=Lax, 30 дней.
- `/` — оболочка: экран выбора (только сразу после входа; при перезагрузке — та же вкладка, где был пользователь) → вкладки:
  **Менеджер → Агент → Расписание → Клиенты → Воронка → Касса → Квалификация → Замеры → Отчёты → Настройки**
  - Настройки — только `admin`.
  - Вкладки — iframe, переключение без перезагрузки.
  - Боковые вертикальные кнопки: левая = предыдущая вкладка (подписана её названием), правая = следующая; на первой нет левой, на последней нет правой; бейджи уведомлений и на них; на телефоне только верхние вкладки.
  - Повторный клик по активной вкладке возвращает её на начальный экран.
- **Агент** («овчарка») — `/window`, код `public/window-app.js`.
- **Остальные вкладки** — React-приложение `kviz/client` (Vite + TS) под путём `/kviz`, API под `/kviz/api/*`.

## 2. Жёсткие правила

### База данных
- **SQL-файлы и миграции НЕ создавать.** Схему пишет Claude в чате, Сергей выполняет вручную в Supabase SQL Editor. В ТЗ обычно сказано «SQL уже выполнен».
- Перед работой с таблицей проверь её реальные колонки и ограничения: `select column_name, data_type, is_nullable, column_default from information_schema.columns where table_name = '...'` и `select conname, pg_get_constraintdef(oid) from pg_constraint where conrelid = '<таблица>'::regclass`. **Код подгоняется под базу, а не наоборот.** Не придумывай имена колонок и значения полей.
- Поля с `check (... in (...))` — в форме только выпадающий список с этими значениями. Поля с `default` в базе — пустое значение из формы отправлять как default (обычно 0), не `null`.
- Генерируемые колонки (`total_cm`, `phone_digits`) и номера, которые ставит триггер или bigserial (`measure_no`, `number`), в insert не передавать.
- Если для задачи не хватает колонки или таблицы — остановись и напиши, какой SQL нужен, не обходи это в коде.
- Сырые ошибки Postgres пользователю не показывать: сервер проверяет данные до записи и отвечает понятным русским текстом, ошибку базы — только в лог.

### Своя CRM (`crm_*`)
- Продажа и возврат — ТОЛЬКО через rpc `crm_checkout(jsonb)` и `crm_refund(jsonb)` (одна транзакция в базе). Не собирать продажу отдельными insert'ами.
- У CRM-таблиц есть `branch_id` (сейчас один филиал `00000000-0000-0000-0000-000000000001`). Не терять его в запросах — дальше будет мультифилиальность.
- Удаление в справочниках: «В архив» и «Удалить»; удалять только если запись нигде не используется, иначе объяснить и предложить архив.
- Все изменения CRM-данных — в `crm_audit_log`.
- С Fitbase из CRM только читаем (импорт), ничего не пишем.

### Fitbase API
- `page_size` — **не больше 100.** Всегда пагинация до пустой/неполной страницы, пауза 300–500 мс между страницами.
- Ошибки 4xx (валидация) не ретраить. Общий circuit breaker агента не обходить.
- Флаги `*_DRY_RUN` уважать: в DRY ничего не менять в Fitbase. У агента жизненного цикла (`lifecyclePlan`) флага DRY нет — его не трогать и не запускать без явной просьбы.
- Чат Fitbase = сервис EasyChat (`chat.easychat.ru`) во фрейме. API чатов нет.

### Данные
- Телефоны в старых таблицах агента — `+7XXXXXXXXXX`, поиск через `phone_digits`. В таблицах `crm_*` и `script_*` телефон хранится только цифрами `7XXXXXXXXXX`. Не смешивать — смотри колонки таблицы.
- Часовой пояс — `Asia/Yekaterinburg` (UTC+5). «Сегодня», смены, задачи, тревоги — по этому поясу, считать на сервере.
- Автор записи (консультант, кассир, кто отметил задачу) — `display_name` из сессии, на сервере. Не просить вводить имя.
- ИИН и данные удостоверений — только в открытой анкете; в списках маскировать.

### Вход и маршруты
- Один middleware входа на всё. Страницы без входа → редирект на `/login?returnTo=...`, любые `/api/*` без входа → **401 JSON, никогда не редирект.**
- Внутри вкладок (iframe) своих форм входа и редиректов нет. При 401 вкладка шлёт родителю `postMessage({ type: 'auth-required' })`.
- Прямой заход на `/window` или `/kviz/*` как документ (`Sec-Fetch-Dest: document`) → редирект на `/`. Поэтому **ничего не открывать новым окном** (печать, превью и т. п.) — только внутри текущей страницы (скрытый iframe, модальное окно). Никаких `alert()` — только встроенные окна и тосты.
- Порядок маршрутов: `/kviz/api`, static `/kviz` и SPA-fallback `/kviz/*` — раньше любых catch-all.
- Cron-эндпоинты `/run/*` и `/health` не ломать.
- `/scriptolog` открывается в iframe расширения: вход по Bearer-токену, не по cookie.

### Справочные материалы
- `crm-reference/` — только примеры. Код своей старой SlimWay CRM можно переносить. Из Frappe CRM (лицензия AGPL) брать только идеи и подходы, код не копировать. Сводка — `docs/crm-reference-map.md`.

### Секреты
- Никаких паролей, токенов и ключей в коде и коммитах. Всё через env (Render → Environment), локально — `.env` (в `.gitignore`).
- Основные env: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `FITBASE_TOKEN`, `FITBASE_CLUB`, `CRON_SECRET`, `SMTP_USER`, `SMTP_PASS`, `ALERT_EMAIL`, `WATCH_RULES`, `TRIAL_AGENT_DRY_RUN`, `BUDGET_DRY_RUN`, `INACTIVE_DRY_RUN`, `SHIFTS_SHEET_WEBHOOK_URL`, `SHIFTS_SHEET_SECRET`, `RESULTS_DISPLAY_KEY`.

### Интерфейс
- Язык интерфейса — русский. Деньги — `₸`, пробелы между тысячами.
- Стиль — светлый воздушный glassmorphism, фирменные цвета `#02BDB6` (основной) и `#263CD9` (акцент).
- Каждый экран проверять на ширине 1440, 1024 и 375 px: без горизонтальной прокрутки страницы, текст не налезает.
- Страницы внутри вкладок занимают всю ширину вкладки, если в задаче не сказано иначе. Боковые панели разделов — слева.

## 3. Очередь задач и передача работы

- Все задачи и их статусы — в `docs/QUEUE.md`, полные ТЗ — в `docs/tasks/`. Если у одного агента кончились лимиты, другой открывает очередь и продолжает с того же места.
- Если Сергей дал задачу текстом в чате — сохрани её в `docs/tasks/NN-модуль-название.md` (первая строка `Модуль: <имя>`) и добавь в очередь, прежде чем начинать.
- Начинаешь задачу — поставь статус «в работе» и закоммить очередь.
- Если работа прервалась на середине — перед остановкой закоммить то, что собирается, и запиши в «Журнал» очереди и в файл модуля, что сделано и что осталось.

## 4. Порядок работы (обязательно)

1. **Один агент за раз.** Перед началом: `git pull --rebase origin main` и `git status` — рабочая папка должна быть чистой. Если есть чужие незакоммиченные изменения — остановись и сообщи.
2. Прочитай файлы из раздела 0.
3. Выполняй задачу **целиком**, по всем частям ТЗ. Если что-то не получилось — так и напиши в отчёте, не пропускай молча.
4. `npm run build` — без ошибок.
5. Обнови документацию (раздел 8).
6. Коммит с понятным сообщением → `git push origin main`.
7. **Дождись деплоя на Render** этого коммита (1–2 минуты) и проверь результат **на живом сайте**. Для интерфейса — скриншоты.
8. Не писать «готово», пока проверка на проде не прошла.
9. Временные файлы (скриншоты, `img/`, `png/`, `result.md`) не коммитить.

## 5. Формат отчёта в конце

- Хэш коммита(ов).
- Таблица по частям ТЗ: часть → сделано / частично / не сделано → комментарий.
- Что проверено на проде (и скриншоты для UI).
- Нужен ли SQL, новые env в Render или новое расписание в cron-job.org — точным текстом.
- Какие файлы `docs/` обновлены.
- Список изменённых файлов.

## 6. Режим ревью (когда просят проверить чужой коммит)

- Ничего не менять, не коммитить.
- Взять ТЗ и коммит(ы): `git log`, `git show <хэш> --stat`, `git diff`.
- Пройти ТЗ по пунктам: выполнено / частично / не выполнено, с файлом и строкой.
- Отдельно: баги, нарушения правил из этого файла, риски для агента и cron.
- По возможности проверить на живом сайте.

## 7. Модули и чаты

Работа разделена по модулям. У каждого модуля свой файл `docs/modules/<имя>.md` и свой чат у Сергея в claude.ai (проект «Fitbase автоматизация»). Список модулей и их чатов — в `docs/STATE.md`.

Чаты claude.ai пишут ТЗ и SQL, а Claude Code выполняет. Чат перед ТЗ читает эти же файлы с компьютера Сергея (`C:\Users\SKUPKA\Desktop\agent`), поэтому файл модуля должен быть всегда актуальным — это единственная память между чатами.

## 8. Обновление документации после задачи (обязательно)

В том же коммите, что и код:

1. **`docs/modules/<модуль>.md`:**
   - В «Сделано» добавь запись **сверху**: `### ДД.ММ.ГГГГ · <хэш> · <название задачи>` и 2–6 строк: что сделано и **как** (какие файлы/эндпоинты/таблицы, ключевая логика). Коротко, без воды.
   - Обнови «Где код», «Таблицы», «Ключевые решения», если появилось новое.
   - «Открытые баги»: убери исправленные, добавь найденные.
   - «Следующее»: убери сделанное.
   - Если в ТЗ было «не делать сейчас / важно на потом» — перенеси это в «Следующее» с пометкой.
2. **`docs/STATE.md`:** обнови строку модуля (статус, дата, одна фраза о последнем изменении).
3. **`docs/QUEUE.md`:** статус задачи + строка в «Журнал».
4. Если изменились общие правила или оболочка (вкладки, вход, маршруты) — обнови этот файл и `AGENTS.md` (они одинаковые).

Пиши для того, кто откроет файл через месяц без контекста: что есть, где лежит, почему так решено.
